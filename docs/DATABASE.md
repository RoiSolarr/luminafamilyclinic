# Database

PostgreSQL, organised into three schemas by domain rather than one flat `public`
schema. Drizzle ORM maps them with `pgSchema()`, and the migration in
`db/migrations/0000_init.sql` is hand written so it can carry the pieces Drizzle
cannot express: a partial unique index, row level security, and the
`updated_at` triggers.

| Schema | Holds | Tables |
| --- | --- | --- |
| `core` | The organisation and who may act for it | `organizations`, `organization_members` |
| `medical` | Clinical and scheduling data | `providers`, `services`, `provider_services`, `provider_schedules`, `patients`, `appointments` |
| `communications` | Messages in, messages out, ratings | `contact_messages`, `reminders`, `feedback` |

Conventions used throughout:

- `uuid` primary keys, generated by `gen_random_uuid()` from `pgcrypto`.
- `snake_case` column names.
- `created_at` everywhere, `updated_at` on anything that is edited after insert.
- Every foreign key is indexed.
- Postgres enum types for every status and category field.
- Row level security enabled on all eleven tables, with no policies.

## Schema `core`

### `core.organizations`

One row per clinic. The demo seeds exactly one, found by the `slug` in
`config/clinic.ts`.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` | Primary key |
| `name` | `text` | Display name |
| `slug` | `text` | Unique. The application looks the row up by this |
| `timezone` | `text` | IANA name. Every slot calculation runs against it |
| `phone`, `email`, `address` | `text` | Shown in the footer and on contact pages |
| `settings` | `jsonb` | See below |
| `created_at`, `updated_at` | `timestamptz` | `updated_at` maintained by trigger |

`settings` carries the booking rules, so they can change without a migration:

```json
{
  "slotMinutes": 30,
  "bookingWindowDays": 60,
  "minNoticeHours": 2,
  "holidays": ["2026-12-25", "2027-01-01"],
  "closedWeekdays": [0]
}
```

### `core.organization_members`

Staff who may act for the clinic. The demo dashboard uses a single shared
password rather than these rows; they are here so a real deployment can move to
per person sign in without a schema change.

Unique on `(organization_id, user_email)`. Role is `owner`, `admin` or `staff`.

## Schema `medical`

### `medical.providers`

The doctors. `languages` is a `text[]`, `initials` drives the avatar so no
photographs are needed. Deactivating a doctor is `is_active = false`, which
hides them from booking while keeping their history intact.

### `medical.services`

What can be booked. `duration_minutes` is the real length of the appointment and
drives slot generation. `price_min` and `price_max` are `numeric(10,2)` with a
check that the max is not below the min.

Unique on `(organization_id, slug)`, because the slug appears in URLs such as
`/book?service=dermatology`.

### `medical.provider_services`

The join table deciding which doctor offers which service. Composite primary key
on `(provider_id, service_id)`, indexed from both sides so the booking wizard can
filter in either direction.

### `medical.provider_schedules`

Recurring weekly hours in clinic local time. `day_of_week` is 0 for Sunday,
constrained to 0 to 6, and `end_time` must be after `start_time`.

A doctor may have several rows for one day, which is how a morning and an
afternoon clinic with a lunch break in between are expressed. An appointment has
to fit inside a single row: a 60 minute service cannot straddle the gap.

### `medical.patients`

Unique on `(organization_id, email)`. The booking route upserts on that pair, so
a returning patient updates their record instead of creating a duplicate.

`consent_given_at` records when the consent checkbox was ticked.

### `medical.appointments`

The centre of the model.

| Column | Notes |
| --- | --- |
| `booking_ref` | Unique, format `LFC-XXXXXX`, enforced by a regex check constraint. Drawn from an alphabet with no confusable characters, so it survives being read over the phone |
| `starts_at`, `ends_at` | `timestamptz`, absolute instants. Wall clock time is derived for display |
| `status` | `pending`, `confirmed`, `cancelled`, `rescheduled`, `completed`, `no_show` |
| `manage_token_hash` | SHA-256 of the patient's token. The raw token is never stored |
| `ai_urgency`, `ai_summary`, `ai_red_flag`, `ai_confirmation_message` | Written only by the Zapier callback |
| `calendar_event_id` | Written by the callback after the calendar event is created |

Indexes: `booking_ref` (unique), `organization_id`, `patient_id`, `service_id`,
`(provider_id, starts_at)` and `(status, starts_at)`.

#### The double booking guard

```sql
CREATE UNIQUE INDEX appointments_live_slot_key
  ON medical.appointments (provider_id, starts_at)
  WHERE status IN ('pending', 'confirmed');
```

This is the part that actually prevents a double booking, and it is worth being
precise about why it is an index rather than application logic.

Two patients can both load the availability endpoint, both see 10:00 free, and
both submit. Application checks cannot close that window, because between the
check and the insert the other transaction can commit. The index closes it in the
database: both inserts are attempted, one succeeds, the other raises `23505`, and
`POST /api/book` turns that into a 409 with a friendly message.

The `WHERE` clause is what makes cancelling free the slot. A cancelled row drops
out of the index, so the next patient can take the same `(provider_id,
starts_at)` with no cleanup job.

For `any available doctor`, the booking route tries each rostered, eligible
doctor in turn inside a savepoint. A `23505` on one simply moves to the next
candidate, and only when all of them are taken does the patient see the 409.

## Schema `communications`

### `communications.contact_messages`

Everything from the contact form and the FAQ page. `topic` is what the sender
picked; `ai_topic` is what the automation classified it as, kept separate so the
two can be compared. `ai_draft_reply` is for staff review and is never sent
automatically.

### `communications.reminders`

One row per message that should go out. Unique on `(appointment_id, type)`, so a
retry cannot produce two reminders of the same kind for one appointment.

`GET /api/zapier/due-reminders` reads rows where `status = 'pending'` and
`scheduled_for <= now()`, joined to appointments that are still live.

Cancelling an appointment sets its pending reminders to `failed` with a reason,
so nothing goes out for an appointment that is no longer happening.

### `communications.feedback`

Unique on `appointment_id`, so a patient rates a visit once. Rating is
constrained to 1 through 5.

## Row level security

Every table has RLS enabled and **no policies at all**:

```sql
ALTER TABLE medical.appointments ENABLE ROW LEVEL SECURITY;
```

With RLS on and no policy, any role subject to RLS sees an empty table. On
Supabase that means the `anon` and `authenticated` roles, which is exactly what
the PostgREST API and any leaked publishable key would use. The three schemas are
also revoked from `PUBLIC`, `anon` and `authenticated`, so they are not exposed
through the data API in the first place.

`FORCE ROW LEVEL SECURITY` is deliberately **not** used. The application connects
as the owner role, which bypasses RLS; forcing it would lock the application out
of its own tables. The security boundary for this project is the connection
string, which lives only in a server side environment variable, plus the
application's own validation and token checks.

## Scripts

| Command | Does |
| --- | --- |
| `npm run db:generate` | Runs `drizzle-kit generate` to diff the TypeScript schema and write a new migration |
| `npm run db:migrate` | Applies pending migrations, using `DIRECT_DATABASE_URL` when set |
| `npm run db:seed` | Rebuilds the demo clinic. Deletes the Lumina organisation first, so it is safe to re-run |
| `npm run db:drop -- --yes` | Drops all three schemas plus `drizzle` |
| `npm run db:reset` | Drops, migrates and seeds in one command. Prints the host first |

A note on `db:generate`: migration `0000_init.sql` is hand written, so there is
no matching Drizzle snapshot in `db/migrations/meta`. The first time you run
`db:generate` it will therefore want to write a full baseline rather than a diff.
For iterating on the schema during development, `npx drizzle-kit push` is the
better tool; reach for `db:generate` once you are ready to start a proper
migration history from the current state.

## What the seed creates

Run against an empty database, `npm run db:seed` produces:

- 1 organisation
- 3 members (owner, admin, staff)
- 6 services
- 6 doctors with 32 schedule blocks between them
- 15 appointments spread across the previous week and the next two
- 5 contact messages in various states
- reminders for every live appointment, and feedback on completed ones

Appointments are placed relative to the day you run the seed, and each one is
snapped forward or backward to a time its doctor is actually rostered for, so the
demo never contains an appointment outside clinic hours.
